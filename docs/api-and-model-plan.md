# 필요한 API / 알고리즘·모델 정리

지금 `dajim-web`은 [`lib/mockData.ts`](../dajim-web/lib/mockData.ts) 하나에 있는 목데이터로 전 화면이 동작합니다. 이 문서는 그 목데이터를 실제 데이터로 바꾸는 데 필요한 백엔드 API와, API 뒤에서 실제로 값을 계산해야 하는 알고리즘/모델을 정리한 것입니다. 각 항목은 대체할 mock 함수를 기준으로 묶었습니다.

## 1. 백엔드 API

| API | 대체하는 mock 함수 | 설명 |
| --- | --- | --- |
| `POST /auth/login`, `GET /users/me` | `getUser()` | 로그인/회원 정보. 온보딩의 "계좌 연결하고 시작하기" 이전 단계 |
| `POST /accounts/link`, `GET /accounts` | (사이드바 "연결 계좌 2개") | 오픈뱅킹 또는 카드사 연동 인증 흐름. 연결된 계좌/카드 목록 조회 |
| `GET /transactions?from&to&account&category` | `getTransactions()` | 연동된 계좌·카드의 원본 거래내역 + 카테고리 태그 |
| `POST /goals`, `GET /goals/current`, `PATCH /goals/:id` | `useGoalSettings` (현재 localStorage) | 목표 설정값 저장. 카테고리/기간/감소율/트래킹 주기 |
| `GET /summary/home` | `getHomeSummary()` | 이번 달 총지출, 전월 대비 증감률, 목표 진행률, 다음 트래킹까지 D-day |
| `GET /predictions/scenario?mode=neg\|pos&goalId=` | `getPredictionScenario()` | 예측 모델(§2-2, §2-3)을 호출해 시나리오 문구·수치·추이 반환 |
| `GET /tracking/reports/:goalId/latest` | `getTrackingReport()` | 트래킹 주기(3/7/14일)마다 배치로 생성된 리포트 조회 |
| `GET /goals/:id/result` | `getResultData()` | 목표 기간 종료 시 자동 계산되는 달성/실패 결과 + 재설정 추천 |
| 스케줄러(배치) | — | 유저별 트래킹 주기에 맞춰 리포트 생성, 목표 종료일에 결과 계산 |

계좌 연동은 직접 은행/카드사와 붙기보다 **오픈뱅킹(금융결제원)** 이나 **코드에프(CODEF)/뱅크샐러드 API** 같은 계좌 통합조회 벤더를 쓰는 걸 추천합니다 — 카드사별로 따로 붙는 것보다 개발 비용이 훨씬 적게 듭니다.

## 2. 알고리즘 / 모델

### 2-1. 거래 카테고리 분류기

- **입력**: 가맹점명, (있다면) 업종코드(MCC)
- **출력**: `categoryId` (배달음식/카페/쇼핑/구독서비스…)
- **대체 대상**: `getTransactions()`의 `categoryId`, `getCategory()` 목데이터
- **접근**: 처음엔 가맹점명 키워드 매칭 규칙 테이블로 시작(오픈뱅킹/카드사가 업종코드를 주면 이것만으로도 커버율이 꽤 높습니다). 미분류 가맹점이 쌓이면 그때 텍스트 분류 모델로 고도화 — 초기 단계에 ML부터 넣을 필요는 없습니다.

### 2-2. 소비 추이 예측 모델

- **입력**: 카테고리별 과거 N개월 거래내역(일/주 단위 집계)
- **출력**: 이번 달 예상 소비액, 전월 대비 증감률 — 예측 시나리오 화면의 `+28%`, `trend` 그래프
- **대체 대상**: `getPredictionScenario('neg', ...)`의 `metricValue`, `trend`
- **접근**: 이동평균/선형 추세 외삽으로 시작 → 데이터가 쌓이면 요일·월중 시점 패턴을 반영한 시계열 모델(지수평활, Prophet 등)로 고도화

### 2-3. 목표 달성 시뮬레이션 (what-if)

- **입력**: 2-2의 기준 예측치, 사용자가 설정한 감소율
- **출력**: "목표 달성 시" 예상 소비량/절감액, 저축 목표 달성 가능 여부
- **대체 대상**: `getPredictionScenario('pos', ...)`, `getExpectedSavingWon()`
- **접근**: 처음엔 `기준 예측치 × (1 - 감소율)` 산술 계산으로 충분. 나중에 "배달음식을 줄이면 카페가 늘어난다" 같은 카테고리 간 소비 전이까지 반영하면 정확도가 올라갑니다.

### 2-4. 트래킹 리포트 생성 로직

- **입력**: 목표 시작일, 트래킹 주기, 해당 기간 실제 거래내역
- **출력**: 목표선 대비 실제 소비 곡선, 카테고리별 증감률, `목표 초과 달성 중` 같은 상태 라벨
- **대체 대상**: `getTrackingReport()`
- **접근**: 집계 + 임계값 분류(예: 실제 감소율이 목표의 1.1배 이상이면 "초과 달성")로 시작하면 충분한 영역입니다.

### 2-5. 목표 재설정 추천

- **입력**: 목표 대비 실제 갭, 최근 카테고리별 소비 변화
- **출력**: `기간 연장 / 목표 완화 / 카테고리 변경` 같은 재설정 옵션
- **대체 대상**: `getResultData()`의 `suggestions`
- **접근**: 처음엔 갭 크기에 따라 정해진 템플릿 3종을 규칙으로 조합. 데이터가 쌓이면 실제로 재도전 성공률이 높았던 패턴 기반으로 랭킹을 붙이는 정도면 충분하고, 여기도 처음부터 개인화 모델을 만들 필요는 없습니다.

### 2-6. 저축 목표 산정

- 현재 `320,000원`으로 하드코딩된 값(`SAVING_GOAL_WON`)입니다. 실제로는 사용자의 월 수입/지출 패턴에서 산정하거나, 온보딩에서 사용자가 직접 입력받는 단계가 필요합니다.

## 3. 제안하는 순서

1. **1단계 — API 먼저**: 인증, 계좌 연동, 거래내역 API, 목표 CRUD API, 카테고리는 규칙 기반 분류. 이것만으로도 목데이터를 실데이터로 바꿔서 화면이 "진짜처럼" 동작합니다.
2. **2단계 — 예측 핵심**: 소비 추이 예측(이동평균 수준), 목표 달성 시뮬레이션(산술 계산), 트래킹 리포트 생성. 다짐의 핵심 가치인 "예측 시나리오"가 실제로 계산되기 시작하는 단계입니다.
3. **3단계 — 고도화**: 시계열 모델 정교화, 카테고리 분류 ML화, 재설정 추천 개인화. 데이터가 충분히 쌓인 뒤에 진행해도 늦지 않습니다.
