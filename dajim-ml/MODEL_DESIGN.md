# 거래 카테고리 분류기 — 설계 근거

**금융 AI Challenge 2026 / 소비 악순환 예측 및 시나리오 제공 시스템**
모델 ① 거래 카테고리 분류기 · 담당 정채영 · 2026-08-18

---

## 0. 이 모델이 하는 일과, 왜 중요한가

```
"배달의민족  -23,000원"  →  delivery
"스타벅스 강남점 -5,600원"  →  food
"김철수  -450,000원(이체)"  →  transfer  ← 소비 아님
```

우리 서비스의 **모든 숫자가 이 분류 위에 올라간다.**

```
카테고리 분류  →  카테고리별 소비 예측  →  시뮬레이터  →  ETA
                                                      ↓
                                            "배달 줄이면 38일 단축"
```

배달을 식비로 잘못 넣으면 "배달 줄이기" 추천 자체가 성립하지 않는다.
이체를 소비로 세면 월 지출이 몇 배로 부풀어 ETA가 통째로 틀어진다.
**분류기는 정확도 경쟁을 하는 모델이 아니라, 파이프라인의 전제를 만드는 모델이다.**

## 2. 카테고리 체계 — 왜 247개를 하나씩 안 썼나

### 결정: 중분류 기본값 + 소분류 예외

```
소분류코드 = 중분류코드(4자리) + 2자리
G20404(슈퍼마켓) → G204(종합 소매) → food
```

- **중분류 75개**에 기본값 부여
- **상식과 어긋나는 소분류 12개**만 예외로 덮어씀

### 이유

| | 247개 전부 나열 | **중분류 + 예외 (채택)** |
|---|---|---|
| 유지보수 대상 | 247줄 | 87줄 |
| 오타·누락 발견 | 어려움 | 예외 12개만 보면 됨 |
| 발표 설명 | "247개를 매핑했습니다" | **"중분류 단위로 매핑하고 12개만 예외 처리했습니다"** |
| 신규 업종 추가 시 | 개별 대응 | 중분류 기본값이 자동 적용 |

### 예외 12개와 그 근거

| 소분류 | 중분류 기본값 | 예외 | 왜 |
|---|---|---|---|
| 자전거 소매업 | shopping | **transport** | 이동수단이지 취미용품이 아님 |
| 약국 / 의료기기 | shopping | **medical** | 의약품 지출 |
| 안경렌즈 | shopping | **medical** | 시력 교정 |
| 서점 / 운동용품 | shopping | **leisure** | 여가 소비 |
| 주류 소매 | food | **leisure** | 주점과 동일하게 비필수로 취급 |
| 가정용 연료 | transport | **living** | 주유가 아니라 난방비 |
| 요가·필라테스 학원 | education | **leisure** | 헬스장과 같은 성격 |
| 만화방 / 레저용품 대여 | living | **leisure** | 여가 소비 |

### 카테고리 10개 — 6개가 아닌 이유

시나리오 엔진이 다루는 변동비는 6개(식비·배달·쇼핑·교통·구독·여가)다.
하지만 **분류기는 사용자 거래 전체를 덮어야 한다.**
의료·교육·생활고정·기타를 버리면 그 지출이 통계에서 사라지고 월 소비 총액이 틀어진다.

```
variable  : food, delivery, shopping, transport, subscription, leisure  ← 행동 추천 대상
essential : medical, education                                          ← 줄이라고 말하면 안 되는 지출
fixed     : living                                                      ← 고정비, 시뮬레이터 상수
excluded  : other                                                       ← B2B 등
+ transfer                                                              ← 소비 아님
```

**의료비를 줄이라고 추천하는 서비스는 만들면 안 된다.** 이 구분이 그걸 코드 레벨에서 막는다.

## 3. 왜 단일 ML 모델이 아니라 5단계 캐스케이드인가

### 한 가지 방법으로는 전체를 못 덮는다

| 문제 | 단일 ML | 실제 필요한 것 |
|---|---|---|
| 배달의민족·넷플릭스 | ❌ 학습 데이터에 아예 없음 | 브랜드 사전 |
| "카드대금 이체" | ❌ 소비도 아닌데 카테고리를 찍음 | 이체 필터 |
| "토스페이먼츠" | ❌ 뭘 샀는지 모르는데 확신함 | 미분류 처리 |
| "○○약국" | ⭕ 가능하지만 규칙이 더 정확·빠름 | 키워드 규칙 |
| "라라머시기" | ⭕ **여기가 ML의 자리** | ML |

### 구조

```
L0  정규화        표기 흔들림 제거
L1  이체/PG 필터   소비가 아닌 거래 제거          ← 가장 확실
L2  브랜드 사전    온라인·구독·배달 344개
L3  상호명 사전    상가정보 추출 67,244개
L4  키워드 규칙    업종 단서 250개
L5  ML 폴백        문자 n-gram 나이브베이즈       ← 가장 넓음
```

위로 갈수록 정확하고 아래로 갈수록 커버리지가 넓다.
각 단계는 **자기가 확신하는 것만 처리하고 나머지를 아래로 넘긴다.**

### 실측 결과 (테스트 366,889건 — 학습에 없던 가맹점만)

| 단계 | 커버리지 | 정확도 |
|---|---|---|
| L2 브랜드 사전 | 2.38% | **0.912** |
| L3 상호명 사전 | 8.57% | **0.954** |
| L4 키워드 규칙 | 31.94% | 0.847 |
| L5 ML | 54.23% | 0.653 |
| L5 신뢰도 미달 → 미분류 | 2.87% | — |

**설계 의도대로 위 단계일수록 정확하다.**
만약 L5가 L4보다 정확했다면 키워드 규칙에 오류가 있다는 뜻이므로, 이 표 자체가 검증 도구다.

## 4. 왜 문자 n-gram인가 — 형태소 분석기를 안 쓴 이유

한국어 상호명은 **띄어쓰기가 없거나 제멋대로**다.

```
본죽&비빔밥카페    스타벅스강남점    쭈꾸미불백집    파리바게뜨역삼점
```

| | 형태소 분석기 (KoNLPy 등) | **문자 2~4그램 (채택)** |
|---|---|---|
| 띄어쓰기 의존 | 있음 | **없음** |
| 신조어·브랜드명 | 미등록어로 처리 실패 | 문자 단위라 무관 |
| 의존성 | JVM + 사전 (수백 MB) | **numpy 하나** |
| 배포 | 무료 티어 512MB에 부담 | 문제없음 |

`약국`, `헤어`, `정비` 같은 업종 단서가 문자 단위로 잡히고,
`쭈꾸미불백집`처럼 사전에 없는 이름도 `불백`, `집` 같은 조각으로 신호를 준다.

## 5. 왜 나이브베이즈인가 (그리고 LinearSVC로 가는 길)

### 채택 이유

이 노트북은 **의존성 없이 팀원 누구 환경에서나 바로 도는 것**을 우선했다.
sklearn `TfidfVectorizer + LinearSVC`가 보통 성능이 더 좋지만,
설치 상태가 제각각이면 "제 컴퓨터에선 안 돌아요"로 시간을 버린다.

나이브베이즈는 numpy만으로 구현되고, 학습이 선형 1회 스캔이라 **40만 건에 4초**다.

### 업그레이드 경로

`CharNGramNB`와 sklearn 모델은 인터페이스(`fit` / `predict_one`)가 같다.
sklearn이 있는 환경에서는 교체 실험만 하면 되고, **비교 결과를 발표에 넣으면 그 자체가 근거가 된다.**
현재 F1이 낮은 shopping(0.536)에서 개선폭이 클 것으로 예상된다.

## 6. 개발 중 잡은 문제 3가지

### ① 정규식 지점명 제거가 케이스마다 다르게 동작

`[가-힣]{1,6}점$`으로 '역삼점' 같은 지역 지점명을 지우려 했다.
정규식이 왼쪽부터 매칭하는 바람에 결과가 갈렸다.

```
'김밥천국역삼점'  → '밥천국역삼점' 매칭 → 남는 글자 1자 → 스킵 (제거 실패)
'gs25서울대점'   → '서울대점' 매칭    → 정상 제거
```

어느 글자가 지역명인지 규칙으로 알 방법이 없다.
**규칙을 정교하게 만드는 대신 매칭 방식을 바꿨다.**

- 정규화는 `본점 / 2호점 / 1층` 같은 **명시적 표기만** 제거
- 지역 지점명은 사전 단계에서 **접두어 매칭**으로 흡수

한국 상호는 브랜드가 앞, 지점이 뒤에 오므로 접두어 방향이 구조적으로 맞다.

### ② 부분 문자열 매칭으로 멀쩡한 가맹점 133곳을 지웠다

이체 판별을 `["이체","대출","주식","세금",...] 포함`으로 짰더니:

```
성주식당            → '주식'  에 걸림
한국세탁소           → '국세'  에 걸림
현대출력센타          → '대출'  에 걸림
커피빈여의도교보증권점    → '증권'  에 걸림
```

**카테고리를 틀리는 것보다 나쁘다.** 지출 자체가 통계에서 사라진다.

수정:
1. **CSV의 `거래유형` 컬럼을 1순위로** 사용 — 가맹점명 추측은 폴백일 뿐
2. 가맹점명 판별은 **정확 일치 + 앵커된 패턴**만 (`^카드대금`, `이체$`)

실제 카드사 CSV에는 거래유형 컬럼이 거의 항상 있다.
**있는 정보를 안 쓰고 이름에서 추측하려 한 게 애초에 설계 실수였다.** → 오탐 133건 → 2건

### ③ 신뢰도가 전부 0.9999로 나왔다

나이브베이즈는 n-gram을 독립으로 가정해 확률을 전부 곱한다.
글자가 길수록 로그점수 차이가 벌어져 softmax가 항상 1.0에 붙는다.
**신뢰도가 전부 1.0이면 임계값으로 '모름'을 걸러낼 수 없다.**

n-gram 개수로 나눠 '평균 로그확률'로 바꾸니 길이에 무관한 신뢰도가 나왔다.

```
행복한동네정육 → food     0.982
zzqx        → leisure  0.332   ← 낮은 신뢰도 = 미분류 처리 가능
```

| 카테고리 | support | precision | recall | F1 |

### macro-F1에서 delivery·subscription을 뺀 이유

상가정보는 오프라인 점포 데이터라 **배달·구독 표본이 0건**이다.
이 둘을 0점으로 넣으면 macro-F1이 0.731 → 0.532로 떨어지는데,
이건 **모델이 못 맞힌 게 아니라 평가할 데이터가 없는 것**이다.
0점으로 보고하면 실제보다 나쁘게 보이고, 원인도 감춰진다. 별도 명시가 맞다.

→ 이 둘은 **§8 실전 표기 테스트**로 따로 검증했고, 전부 정답이었다.

### 두 개의 테스트 셋을 쓴 이유

**상가정보 테스트만 보면 서비스 정확도를 잘못 읽는다.**

| | 상가정보 테스트 | 실전 표기 테스트 |
|---|---|---|
| 구성 | 학습에 없던 가맹점 366,889건 | 실제 카드 표기 46건 (수기 라벨) |
| 성격 | 동네 개인 가게 위주 = **최악 조건** | 온라인 브랜드·이체·PG 포함 |
| 정확도 | 0.728 | 1.000 |
| 답하는 질문 | 처음 보는 가게를 맞히는가 | **실제 서비스에서 동작하는가** |

실전 표기 46건은 팀원 누구나 자기 카드 내역을 보고 추가할 수 있게 노트북에 넣어 뒀다.
**100건까지 늘리는 게 다음 주 과제다.**

### 커버리지 관점 차이

```
고유 상호명 기준 사전 커버리지 :  3.67%   ← 위 평가가 보는 세계
실제 거래(행) 기준 커버리지    : 18.62%   ← 서비스가 보는 세계 (5.1배)
```

실제 카드내역은 체인점 비중이 상가정보보다 높으므로 L3 비중이 더 커질 것으로 예상되지만,
**이건 아직 추정이다. 실제 카드내역 샘플로 검증해야 한다.**

## 8. 미분류를 남기는 설계

임계값을 올리면 정확도는 오르고 미분류가 는다.

| 임계값 | 미분류율 | 분류건 정확도 |
|---|---|---|
| 0.30 | 0.1% | 0.735 |
| **0.45 (채택)** | **2.9%** | **0.749** |
| 0.60 | 9.9% | 0.780 |
| 0.80 | 19.7% | 0.825 |

**우리 서비스에서는 미분류가 오답보다 낫다.**

- 오답 → 소비 예측·ETA·행동 추천이 **조용히** 틀어진다. 아무도 모른다
- 미분류 → 사용자에게 **"이 거래는 어떤 항목인가요?"** 라고 물어볼 수 있다

물어본 답을 사전에 추가하면 **쓸수록 정확해지는 구조**가 된다.
API 응답에 `unknown` 목록을 담아 보내는 이유가 이것이다.
